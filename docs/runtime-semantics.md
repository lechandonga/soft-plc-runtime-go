# 扫描与故障语义

## 循环扫描三（四）阶段

每个扫描周期严格按顺序执行，全部由运行时单把互斥锁串行化：

1. **输入采样**：通过 I/O 接口一次性 `Read` 整包输入到过程映像。整包快照在本周期内不变，
   程序执行期间外部设备如何更新都不会被当前周期看到（无半更新输入）。
2. **程序执行**：在过程映像上跑完整程序；输出只写输出映像，不对外部设备产生任何效果。
   执行前保存“周期前完整快照”，执行异常时整份回滚，周期内的中间写入一个都不保留。
3. **输出提交**：一次性 `Write` 整包新输出映像，外部只看到完整新包（无半更新输出）。
4. **保持提交**（启用时）：从已提交状态抽取保持项，原子写入保持文件（见 `docs/retain.md`）。

只有四阶段全部成功，扫描计数才加 1，并把当前数据表登记为“最近一次完整提交状态”。

## 确定性与可复现

- 输入采样是整包快照；执行阶段不访问任何外部输入。
- 定时器以 `scan_period_ms` 为固定时间基，不用墙钟累计，因此相同输入序列与配置产生逐拍相同结果
  （见 `TestScanConsistency`：两次独立运行的边沿轨迹逐拍一致）。
- 边沿检测历史以指令位置为键；计数器在输入的上升沿动作，复位具有优先级。

## 看门狗（单周期超时）

单周期保护有两道，互相独立、互不替代，谁先触发算谁：

1. **指令条数预算**（`watchdog_instructions`，默认 100000）：每条指令执行前扣减，
   超预算立即停止执行。故障明细为“单周期指令数超过预算”（`WatchdogError`）。
2. **墙钟耗时上限**（`watchdog_time_ms`，默认 `0` 关闭；设置正毫秒数开启）：
   从本周期**输入采样之前**起计时，覆盖“输入采样 → 程序执行 → 输出提交”全过程。
   检查点为采样后、每条指令边界、提交后；总耗时达到上限即判超时，
   故障明细为“单周期墙钟耗时 Xms 超过上限 Yms”（`DeadlineExceededError`）。

两道保护都进入 `WatchdogFault`，但明细与错误类型把“时间到点”和“条数超了”明确区分开；
在同一条指令边界两道同时到点时记墙钟原因。墙钟判定只发生在上述确定性检查点，
程序因此总能在有限指令步内被终止，不会卡死进程。

### 模拟 I/O 的开销边界

墙钟上限包含采样/提交的真实耗时，因此它能兜住“指令没几条、但就是跑得慢”；
同时本地模拟 I/O 的正常读写开销（内存拷贝量级）不会误报——
`TestWallClockDeadlineNoFalsePositive` 分别用注入的虚拟时钟（开销钉死）和真实时钟连跑多拍
覆盖“不误报”，用固定虚拟耗时的慢采样/慢执行/慢提交覆盖“真超必报”。
这些用例不依赖机器快慢，反复跑、`-race` 下结论一致。

## 执行故障演练（仅本地演练，默认关闭）

生产环境无法确定性地撞上“程序自己出错”，因此提供一个显式演练开关，
仅用于本地把执行异常故障链路完整走一遍：

- 配置 `exec_fault_scan`（必填，1 基扫描尝试序号）开启；可配 `exec_fault_scan_end`
  给出闭区间命中窗口（窗口内第一个到达周期触发）；
  `exec_fault_after_instructions` 指定异常在命中周期第几条指令执行完之后抛出
  （`0` = 第一条指令执行前）。
- 整个配置代内只**确定性地触发一次**；热重载换新配置后重新装弹，关闭演练后绝不注入。
- 触发时进入 `ExecutionFault`（明细含“执行故障演练”），与 `IOFault`（I/O 失联）、
  `WatchdogFault`（超时）、`RetainFault`（保持写入失败）一眼可区分。

演练触发后的处置与真实执行异常完全相同：

1. 当轮整体回滚——异常点之前已执行的半截写入一个不留，异常点之后本周期不再执行；
2. 输出整包落安全值并下发，故障锁存，任何外部条件变化（I/O 重连、输入变化）都不会自愈；
3. 只有满足显式恢复条件并调用 `Recover()` 后，才从**最近一次完整提交的状态**继续，
   而不是从故障周期的半成品往下跑。

关闭演练时（缺省）执行路径不携带任何注入逻辑，正常运行的语义、确定性与并发安全不受影响。

## 故障状态（可区分、锁存、不自动恢复）

| 故障 | 触发 |
| --- | --- |
| `IOFault` | 输入采样失败 / I/O 不健康 / 输出提交失败（含模拟模块断线） |
| `WatchdogFault` | 单周期指令数超预算（条数原因）或单周期墙钟耗时超上限（时间原因，明细可区分） |
| `ExecutionFault` | 执行期异常（地址越界等，解析期无法预见的情形）；含本地演练主动注入 |
| `RetainFault` | 保持快照构造或保持文件提交失败 |
| `StartupFault` | 启动期保持数据不兼容（直接拒绝启动，见保持文档） |

进入任一故障时运行时都会：

1. 回滚到周期前已提交状态（故障周期的半成品全部消失）；
2. 把输出映像整包置为**安全值**（见配置 `safe_outputs`，未列出的输出清 0），并尝试向 I/O 下发；
3. 锁存故障：后续 `Scan` 直接返回该故障，扫描计数不增加——**不会因为 I/O 重连而悄悄自动恢复**。

## 恢复的明确条件（必须显式 `Recover()`）

1. 当前确有锁存故障（正常状态调用恢复会报错，避免把恢复当复位滥用）；
2. I/O 报告 `Healthy()`，且一次试读输入、一次安全值试写都成功；
3. `RetainFault` 还要求保持存储可写：用“最近一次完整提交状态”成功试提交一份保持快照。

恢复后以最近一次完整提交状态为基线继续运行，故障周期的任何中间状态都不存在。
在模拟 I/O 中，`Disconnect()` 后仅 `Reconnect()` 不会恢复扫描，必须再调用 `Recover()`。

## 热重载原子性

`Reload(新源码, 新配置)` 在扫描周期边界整体替换程序：

- 新程序先在临时对象上完成全部启动前校验、保持布局构建与保持文件兼容性判断；
- 任一环节失败：返回 `Applied=false` 与原因（`ValidationRejected` / `RetainIncompatible`），
  **旧程序、旧输出、旧状态原样继续**，不存在新旧指令混执行；
- 全部通过后持锁整体切换 `Program/DataTable/Config/RetainStore`，并立刻整包同步一次新输出映像，
  切换瞬间外部不会看到混合输出。

由于扫描与重载共享同一把锁，二者并发调用只会被串行化（`-race` 下有对应用例）。
